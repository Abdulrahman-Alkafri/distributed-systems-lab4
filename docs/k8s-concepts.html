Kubernetes Objects Explained

Distributed Systems Lab 4 — Pods, ReplicaSets, Deployments, StatefulSets, Services, Ingress

1. What Kubernetes actually does

In Docker Compose you tell the machine what to run. In Kubernetes you describe what you want to exist, and the cluster keeps making reality match that description.

Analogy. Docker Compose is cooking the meal yourself. Kubernetes is telling a kitchen manager "there must always be 3 plates of pasta on the counter". If someone takes a plate, the manager makes another one. You never cook again — you only change the number.

This is called the desired state model. You write a YAML file saying replicas: 3. A controller inside Kubernetes constantly compares desired (3) to actual (2, because a pod crashed) and fixes the difference. This is why Kubernetes "self-heals" — nothing magic, just a loop that never stops checking.

2. Pod — the smallest unit

A Pod is one or more containers that share a network address and storage. In practice, almost always one container = one pod.

Key facts that explain everything else:

  • Every pod gets its own IP address inside the cluster.
  • Pods are disposable. They are never repaired — a broken pod is deleted and a brand-new one is created, with a new name and new IP.
  • Because IPs change, you must never connect to a pod IP directly. That is exactly the problem a Service solves.

You rarely create pods by hand. You create a Deployment or StatefulSet, and it creates the pods.

3. ReplicaSet — keeps N copies alive

A ReplicaSet has exactly one job: make sure a given number of identical pods are running. If you ask for 3 and one dies, it immediately starts a replacement.

You almost never write a ReplicaSet yourself. You write a Deployment, and the Deployment creates the ReplicaSet for you. When you run kubectl get replicaset and see a name like flask-7d4b8c9f5, that is the ReplicaSet the flask Deployment made. The random suffix is a hash of the pod template.

4. Deployment — ReplicaSets plus safe updates

A Deployment manages ReplicaSets so you can change your app without downtime. It is the normal choice for anything stateless — web servers, APIs, workers.

When you change the image version, the Deployment does a rolling update: it creates a new ReplicaSet, starts new pods a few at a time, and scales the old ReplicaSet down to zero as the new pods become ready.

Deployment "flask"
   |
   +-- ReplicaSet flask-7d4b8c9f5  (version 1)  -> 0 pods   <- old, kept for rollback
   +-- ReplicaSet flask-96fd2a71c  (version 2)  -> 3 pods   <- current
                                                   |
                                 +-----------------+-----------------+
                              Pod flask-96fd2a71c-k2xp9  ... -wq4mn  ... -b8rzl

Because the old ReplicaSet is kept, kubectl rollout undo deployment/flask instantly goes back to the previous version.

The hierarchy to remember: Deployment → ReplicaSet → Pod → Container.

5. StatefulSet — for things that store data

A StatefulSet also runs N pods, but it gives each pod two things a Deployment cannot:

GuaranteeWhat it means
Stable namePods are numbered: redpanda-0, redpanda-1, redpanda-2. If redpanda-1 dies, its replacement is called redpanda-1 again — not a new random name.
Stable storageEach pod gets its own disk that follows its name. redpanda-1 always reattaches to the same volume with its own data.
Stable DNSEach pod is reachable at a fixed address: redpanda-1.redpanda-headless.
Ordered startPods start one at a time, 0 then 1 then 2, and shut down in reverse.
Why Redpanda needs this. The three brokers are not interchangeable: each one stores different partition data, and they must find each other by a fixed address to elect partition leaders. With random Deployment names, a restarted broker would get a new identity and a new empty disk, and the cluster would break.

6. Service — a stable address for changing pods

Pods come and go with new IPs every time. A Service is a permanent name and IP that automatically points at whichever pods are currently alive.

It finds its pods using labels, not names:

Service "redis"              Pod labels
  selector:                    app: redis    <- matched
    app: redis                 app: flask    <- ignored

So your Flask code simply connects to the hostname redis, forever, no matter how many times the Redis pod is recreated. Kubernetes runs an internal DNS server that resolves Service names.

The four kinds of Service

Why Lab 4 uses a headless Service for Flask. The assignment requires Nginx to balance with random two least_conn — it must see each pod separately to compare their connection counts. A normal ClusterIP Service would hide the three pods behind one IP and balance them itself, so Nginx would only ever see a single backend and its algorithm would do nothing. Headless gives Nginx all three pod IPs so it can do the balancing.

7. Ingress — one smart HTTP door

An Ingress is an HTTP/HTTPS router at the edge of the cluster. It reads the hostname and URL path of each request and forwards it to the right Service.

                        /api    -> Service api
Internet -> Ingress --> /shop    -> Service shop
                        /        -> Service web

An Ingress object is only a rule list. It does nothing on its own — you also need an Ingress Controller (itself usually an Nginx pod) that reads those rules and performs the routing. In minikube you enable one with minikube addons enable ingress.

Lab 4 uses NodePort, because the assignment asks for Nginx itself to be the gateway that terminates TLS and runs the hybrid load-balancing algorithm. Our Nginx pod is effectively playing the role an Ingress Controller would play — that is why no Ingress object is needed.

8. Storage: PersistentVolume and PersistentVolumeClaim

A container's filesystem is erased when the pod is replaced. To keep data you need a volume.

ObjectMeaning
PersistentVolume (PV)An actual piece of storage in the cluster (a disk).
PersistentVolumeClaim (PVC)A request for storage: "I need 1 GB". Kubernetes finds or creates a matching PV and binds them.
StorageClassThe recipe used to create a PV automatically. minikube's default is standard.
volumeClaimTemplatesOnly in a StatefulSet: creates one PVC per pod automatically — data-redpanda-0, data-redpanda-1, data-redpanda-2.
Analogy. The PVC is the hotel booking ("one room, one night"). The PV is the actual room. You deal with the booking; the hotel assigns the room.

12. The one-paragraph summary

A Pod runs your container but is disposable. A ReplicaSet keeps a fixed number of identical pods alive. A Deployment manages ReplicaSets and gives you safe rolling updates and rollbacks — use it for stateless things. A StatefulSet does the same but gives each pod a permanent name, DNS entry and private disk — use it for databases and brokers. Because pods keep changing IP, a Service provides a permanent address: ClusterIP for internal traffic, NodePort to open a port to the outside, and headless when a client needs to see each pod individually. An Ingress sits above Services and routes HTTP by hostname and path through a single entry point.
